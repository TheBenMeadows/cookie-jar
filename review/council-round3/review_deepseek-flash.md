## 1. Correctness — ranked

**a. `Home.tsx:62` reads ten payments and then explains the absence as a ten-day pruning.** `fetchJarHistory(connection, SHOWCASE_JAR, 10)` returns at most 10 payments; `paymentsForRef` filters *that* array. The `none` branch at `Home.tsx:120` then asserts a cause it never measured: "older than what the public RPC still holds, about ten days." The demo jar is the one address judges' own `TAB-` payments and the refresh job both land on, and each composed payment contributes one or two rows. Ten payments of traffic after the last `LANDING-COMPOSED` landing evicts it from the window, and the homepage then displays a specific, checkable falsehood together with a link that will read "Paid". This is the most likely failure at judging time because it is caused by the traffic the page is built to attract. The read already knows the difference — `history.stoppedAtLimit` is true in exactly that case — and the proof type has no state that can carry it.

**b. `Jar.tsx:157` collapses two different facts into one.** `fetchTxDetail(...).catch(() => null)` maps "the node no longer holds this transaction" and "the RPC refused the call" to the same `null`, and `Jar.tsx:278` renders nothing for either. The receipt then shows a signature link with no shape and no word about why — precisely the "listed but will not return" case, where the honest sentence is short and available. Round 2 fixed one instance of this (absence vs. edge-of-read); this is a new one.

**c. `Home.tsx:122` also predicts wording it has not read.** The `none` copy tells the reader their receipt "reads 'no record' rather than guessing". Run `coversAbsence` over the same jar: if the scan hit the cap, `readToTheEnd` is false and the receipt reads "No record"; if it read to the end, the receipt reads "Not paid" (`Jar.tsx:230`). The homepage states one of two outcomes as fact, and can name the wrong one. Both lines should say what the read did (`limit` hit, cap hit) rather than narrate the RPC's retention policy.

**d. Effect/state races are clean.** Both new effects guard with `live`, and neither `details` nor `proof` survives a `refFilter` change: the route change unmounts. The genuine `details` staleness is different — `Object.fromEntries(entries)` replaces the whole map, so the second `refFilter` render has *no* shapes for the first frame, and rows above `DETAILED_PAYMENTS` never get one. Silent, not false.

## 2. The reference

`byte % 32` over a 32-character alphabet is exactly uniform (256 = 8×32), so no modulo bias. `crypto.getRandomValues` needs no secure context — only `crypto.subtle` does — so `file://`, `http://` on LAN, and every browser this app targets are covered; `globalThis.crypto` is the only real floor, matching the rest of the source. The honest problem is arithmetic, not cryptography: 32⁶ is 2³⁰ ≈ 1.07e9, and all presses land on *one* jar, so this is a birthday problem across a single demo's traffic. At 10,000 presses the chance of at least one collision is about 4.6%; at 50,000 it is about 70%. A collision does not lose funds, but it merges two visitors' receipts into "2 payments carrying this reference" and hands the second visitor someone else's transaction as their receipt. Six characters is one too few for a shared namespace — seven costs nothing on a QR code.

The link is fine: the reference is not a secret, and nothing in the design treats it as one. But see the copy in §5.

## 3. `summarizeTransaction`

`venues` is computed from top-level `message.instructions` only (`txdetail.ts`). On this exact composed checkout the top-level non-housekeeping program **is the router** — inner instructions are where the venue appears — so the line renders "swap through cpamdp…n1sGG" and would print that same program for every route the router takes. "Swap through" names the wrong granularity; the honest line is "swaps routed through <id>", or include top-level *and* inner program ids that are not housekeeping. Lookup tables are not a problem: with `maxSupportedTransactionVersion: 0` the parsed message still carries `programId` for each instruction, and system/compute-budget/ATA/token accounts being housekeeping means the venue list stays one entry — which is what the verified live read shows.

`hasMemo` is top-level only, while `history.ts`'s `memoText` reads `innerInstructions` too. A memo a program emits is therefore counted by the jar and invisible to `TxShape`; the live check's `detail.hasMemo === true` asserts a property the indexing path does not require. The two readers of one transaction should agree, even if only to say "the memo is inside the program call".

## 4. The judge's path

Registry price missing: `priceUsd` null, `symbol` falls back to the link's `TRASHCOIN`, the fixed amount still computes, so the page works — but the `usd` paragraph renders empty and the judge sees no dollar figure at all, having just been told on the homepage this is "about half a dollar." Two routers disagreeing, or neither quoting: the homepage sentence "quotes both Cookie Chain routers" is static text painted before any quote exists, so it is on screen whether or not a route is found; nothing on the page is wrong, but nothing is contingent either. Exceeds 1,232 bytes: `buildPayment`/`simulatePayment` throw and the judge gets the generic error paragraph with no alternative and no hint that the demo invoice could be settled another way — the homepage copy offers none either. Holding TRASHCOIN already: no shortfall, no swap panel, one transfer plus memo, and the button reads "Pay 700 TRASHCOIN"; the conditional "Hold only COOK?" in the lede covers it, but the `h1` "from whatever you hold" is doing work the path does not always do.

## 5. Cut

"about half a dollar" (`Home.tsx:100`). It is the only number on the page not read from chain — the live check verifies the mint's decimals and asserts nothing about a price — and it will keep being displayed after the price moves. Delete it, or render it from `fetchToken(SHOWCASE_MINT).priceUsd` or nothing at all. Second: "so your receipt is yours" (`Home.tsx:101`) claims an attribution the design explicitly refuses — a reference is text anyone can put in a memo, and the receipt itself says so.
